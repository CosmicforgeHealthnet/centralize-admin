# Section 10 — Backend API catalogs and response contracts

Specification Section 10.1–10.3. Report date: 1 November 2026.

## A. Executive verdict

**SECTION 10 CODE COMPLETE — LIVE SOURCE CERTIFICATION PENDING**

All eleven Section 10.1 API families are served by the existing,
product-neutral Product Admin Protocol v1.1 routes (no parallel Karryam
routes, no generic proxy); the 17 Section 10.2 HQ Bridge contracts are pinned
with exactly the specified methods and paths; Section 10.3 status behaviour
is consistent end to end. The previously refused HQ → Product Admin command
path now forwards governed commands. A generated catalog
([`karryam-admin-api-catalog.json`](karryam-admin-api-catalog.json)) is
checked for drift in CI. Nothing reaches a live source: there is no Bridge
enrollment, so every source-backed capability reports its real blocked state.

## B. Architecture of every call

```
Browser (HQ staff, session + CSRF) -> Central Admin API product gateway (/api/products/...)
  -> Product Integration Core (/internal/pic/v1/products/...)   grants, explicit deny, scope, MFA, product ENABLED, sync gate
  -> Karryam Admin (/internal/product-admin/v1/...)           service HMAC + request-bound staff delegation
  -> pinned Bridge adapter (/internal/karryam-admin/v1/...)    TLS 1.3 mTLS, HMAC v2, Ed25519 staff assertion
```

HQ never calls the Bridge; PIC contains no product-specific branch (static
test); Karryam Admin is the only component holding Bridge trust.

## D. HQ command submission (10.1.4 / 10.3)

`products.submitOperation` (PIC): authorize `operation.submit` (explicit
grant, explicit deny, requested scope ⊆ grant ∩ product scope, MFA ≤ 300 s,
audited, fails closed when audit is unavailable) → validate
`operation-command.v1` (400 `COMMAND_INVALID`) → capability must exist in the
ACTIVE contract (404) and be a COMMAND (400) in state AVAILABLE (403
`DISABLED`) → product operations switched on (403
`OPERATIONS_NOT_ENABLED_FOR_PRODUCT`) → forward the exact bytes with a 30 s
delegation bound to `POST /operations` and those bytes → audit the
forwarding with the command digest. A transport failure after sending
returns 503 with the operation ID (read back, never resubmit blindly).

The operations switch requires `integration.approve` by someone other than
the registration requester and the activator, evidence, the current
revision and an ENABLED product without drift; it is recorded in the
append-only onboarding history and enforced again by a database trigger.

## F. Section 10.3 — HTTP and response policy

| Status | Protocol codes | Meaning |
|---|---|---|
| 200/201/202 | — | authoritative response or durably recorded operation (status field carries `SUCCEEDED`, `FAILED`, `UNKNOWN_OUTCOME`, …) |
| 400 | `INVALID_REQUEST` | invalid, non-canonical or unsupported request/schema |
| 401 | `UNAUTHENTICATED` | missing/invalid identity |
| 403 | `FORBIDDEN`, `DISABLED`, `BLOCKED_POLICY` | not authorized, capability disabled, policy-blocked |
| 404 | `NOT_FOUND` | missing or concealed (another staff member's operation) |
| 409 | `CONFLICT` | version conflict, replay, idempotency conflict, self-approval |
| 429 | `RATE_LIMITED` (**added**) | approved rate limit, retryable |
| 503 | `UNAVAILABLE` | source, policy, audit or synchronization unavailable |

`UNKNOWN_OUTCOME` is an operation state, returned with the original
operation ID, never success and never retried automatically; only owner
readback settles it. Envelopes carry product, correlation ID, as-of,
freshness and coverage; errors carry a sanitized reason, retryability and
the operation ID where relevant; no signing material, configuration or raw
source error bodies. Pagination: bounded page size, stable sort, opaque
continuation tokens bound to staff, capability, collection, scope, filters
and window (Sections 6–8).

`RATE_LIMITED` is an additive protocol 1.1 error code (schemas and OpenAPI
regenerated). An older HQ image would reject such an envelope as invalid
and fail closed; images are released together.
