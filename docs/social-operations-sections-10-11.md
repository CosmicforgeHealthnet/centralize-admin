## Shared Lease Pattern

Both queues use `src/modules/marketing/social-operations/workers/lease.service.js`.

Step 1: recover expired leases in a short transaction:

```sql
UPDATE social_publishing_jobs
SET status = 'RETRY_SCHEDULED',
    next_attempt_at = now(),
    lease_owner = NULL,
    lease_expires_at = NULL,
    heartbeat_at = NULL
WHERE status IN ('CLAIMED', 'RUNNING')
  AND lease_expires_at < now()
```

The action queue uses the same statement against `social_action_jobs`.

Step 2: claim due jobs in a separate short transaction:

```sql
SELECT id
FROM social_publishing_jobs
WHERE status IN ('PENDING', 'RETRY_SCHEDULED')
  AND scheduled_for_utc <= now()
  AND (next_attempt_at IS NULL OR next_attempt_at <= now())
ORDER BY priority DESC, scheduled_for_utc ASC
FOR UPDATE SKIP LOCKED
LIMIT $1
```

Claimed rows are immediately updated to:

```text
status = CLAIMED
leaseOwner = worker id
leaseExpiresAt = now + lease duration
```

Provider I/O happens only after the claim transaction has committed.

Expired lease recovery runs every time an enabled worker loop calls `recoverThenClaim()`. It does not run only at startup. Active unexpired leases and terminal jobs are left untouched.

## Publishing State Transitions

Publication status changes are centralized in:

```text
src/modules/marketing/social-operations/services/publication-status-transition.service.js
```

The shared transition service is used by:

```text
initial publishing execution
POLL_PUBLICATION action execution
PUBLICATION_STATUS webhook processing
future reconciliation callers
```

It owns the exactly-once in-process `SOCIAL_PUBLICATION_SUCCEEDED` rule. A transition to `PUBLISHED` emits success only when the publication moves from a non-`PUBLISHED` state to `PUBLISHED`. Replayed webhooks, duplicate polls, reconciliation seeing an already-published record, or a second processing of the same publish result do not emit another success event.

Success:

```text
SocialPublication.status = PUBLISHED / PROCESSING / AWAITING_USER_ACTION
SocialPublishingJob.status = SUCCEEDED
SocialPublicationAttempt is recorded
SOCIAL_PUBLICATION_SUCCEEDED is emitted for confirmed published success
```

Non-terminal provider acceptance:

```text
PROCESSING -> store PROCESSING, keep publishedAt null, record attempt, mark publishing job SUCCEEDED, ensure one POLL_PUBLICATION action job
AWAITING_USER_ACTION -> store AWAITING_USER_ACTION, keep publishedAt null, record attempt, mark publishing job SUCCEEDED, ensure one POLL_PUBLICATION action job
```

The stable polling idempotency key is:

```text
poll-publication:<publicationId>
```

The poll payload contains safe references only:

```text
publicationId
source
confirmation
```

It does not contain credentials, tokens, private message/comment text, raw webhook payloads, or raw provider responses.

Transient failure before max attempts:

```text
SocialPublication.status = FAILED_RETRYABLE
SocialPublishingJob.status = RETRY_SCHEDULED
nextAttemptAt = retry policy result
lastErrorCategory = RETRYABLE or RATE_LIMITED
```

Permanent failure:

```text
SocialPublication.status = FAILED_PERMANENT
SocialPublishingJob.status = FAILED
lastErrorCategory = PERMANENT / PROVIDER_POLICY / AUTH_REQUIRED
SOCIAL_PUBLICATION_FAILED is emitted
```

After max attempts:

```text
SocialPublishingJob.status = FAILED
SocialPublication.status = FAILED_PERMANENT
lastErrorCategory = RETRYABLE_EXHAUSTED
```

No `DEAD_LETTER` status is used.

Execution loads referenced entities fresh:

```text

```

The worker does not trust stale `payloadJson` text captured at enqueue time. Message/comment text is read from current database rows immediately before connector execution.

Action failures are per-job. A failed `REPLY_COMMENT` does not block an unrelated `SEND_MESSAGE`.

## Action State Transitions

Success:

```text
SocialActionJob.status = SUCCEEDED
SocialActionAttempt recorded
completedAt set
```

Transient failure:

```text
SocialActionJob.status = RETRY_SCHEDULED
nextAttemptAt set
attemptCount incremented
```

Permanent failure:

```text
SocialActionJob.status = FAILED
lastErrorCategory = PERMANENT / PROVIDER_POLICY / AUTH_REQUIRED
no retry
```

After max attempts:

```text
SocialActionJob.status = FAILED
lastErrorCategory = RETRYABLE_EXHAUSTED
```

`POLL_PUBLICATION` behavior:

```text
already PUBLISHED -> no provider call, action attempt recorded, poll job SUCCEEDED, no success event
provider PROCESSING -> transition/store PROCESSING, action attempt recorded, same poll job RETRY_SCHEDULED
provider AWAITING_USER_ACTION -> transition/store AWAITING_USER_ACTION, action attempt recorded, same poll job RETRY_SCHEDULED
provider PUBLISHED -> transition to PUBLISHED, set publishedAt, emit success once, action attempt recorded, poll job SUCCEEDED
provider FAILED_RETRYABLE -> transition/store FAILED_RETRYABLE, action attempt recorded, same poll job RETRY_SCHEDULED
provider FAILED_PERMANENT -> transition/store FAILED_PERMANENT, action attempt recorded, poll job FAILED
```

Poll rescheduling uses the existing retry/backoff policy, including `Retry-After` where supplied. The same action job is rescheduled through `status` and `nextAttemptAt`; new jobs are not created per polling attempt.

Webhook/poll race handling:

```text
PUBLISHED webhook -> central transition emits success once and cancels only PENDING/RETRY_SCHEDULED poll jobs
RUNNING poll after webhook -> reloads already-PUBLISHED publication and completes as no-op success
duplicate webhook or later poll -> no duplicate success event
PROCESSING/AWAITING webhook -> non-terminal state preserved, publishedAt stays null, durable polling remains ensured
```

## Heartbeat and Shutdown

Heartbeat:

```text
status must be RUNNING
leaseOwner must match
heartbeatAt is refreshed
leaseExpiresAt is extended
expired lease recovery clears heartbeatAt
```

Shutdown:

```text
stop claiming new jobs
allow in-flight work through the grace window
stop heartbeat
do not mark in-flight jobs failed just because shutdown started
expired leases are recovered on the next run
```

## Scheduling and Timezones

`SocialPostTarget` stores:

```text
scheduledForUtc
timezone
```

The worker compares UTC only:

```text
scheduled_for_utc <= now()
```

The backend validates that `timezone` is an IANA timezone. The composer/calendar UI remains responsible for converting local wall time to UTC and must surface DST ambiguity or invalid local times for user reconfirmation before approval. Since the Section 8 API accepts `scheduledForUtc` plus `timezone`, DST ambiguity is documented here as a UI reconfirmation requirement rather than a worker-time conversion.
