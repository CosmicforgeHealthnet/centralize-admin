# Advertising Execution operations runbook

Safe defaults are mandatory: master, worker and every provider flag `false`; dry-run `true`; connection write policy `false`; reconciliation worker `false`. Inspect authenticated `/capabilities` and `/health` before any sandbox exercise. A configured provider enum or API version is not readiness.

Operational sequence: create DRAFT; validate its exact version; review issues and expiry; submit the exact fingerprint; collect eligible independent approvals; queue the exact current packet; start workers only in an explicitly approved sandbox; monitor jobs, operations and reconciliation; acknowledge incidents without rewriting them; create a compensation DRAFT when needed and run it through the same validation/approval path.

Kill switches are fail-closed. Policy updates need EXECUTION_ADMIN, optimistic versioning and a reason. A connection policy cannot override a false global environment gate. Emergency-related policy changes require a 2FA-enabled elevated actor and bounded future expiry; no override may bypass capability, credentials, regulated-category policy, secret controls, audit immutability, idempotency or unknown-outcome reconciliation.

Unknown outcome: do not resubmit. Inspect the operation and reconciliation references, allow read-back, and escalate if status remains UNKNOWN. Drift acknowledgment records awareness only. Retry requires EXECUTION_ADMIN, a human reason, a current provider read-back, and fresh capability, policy, approval, fingerprint, expiry, dependency and before-state checks. The retry review, action job, operation/run state and audit row commit atomically. UNKNOWN, permission, validation, policy, immutable-field and unsafe dependency cases are blocked.

Queue construction is one serializable, account-locked transaction: exact plan/packet checks, run, operations, snapshots, compensation link, one active job, aggregate state and `EXECUTION_QUEUED` audit evidence commit or roll back together. Duplicate callers resolve to the same durable run/job identity. A pending unleased job cancels immediately; a claimed job receives a durable cancellation request and only its lease-owning worker may observe, cancel and release it before mutation. RUNNING jobs are not falsely cancelled and require known outcome plus compensation.

Compensation accepts lineage identifiers, a safe PAUSE/UPDATE/DELETE proposal, acknowledgement and reason. The server loads the original plan/run/operation/reconciliation and BEFORE/AFTER snapshots; it never trusts caller-supplied provider state or spend evidence. The resulting plan is DRAFT and follows the normal validation and approval lifecycle.

Local database procedure: validate the Admin target, verify the manifest, run migration safety, replay from empty, prepare the approved local Admin database, assert all 25 tables/20 indexes/7 enums, then verify Prisma drift. Never point these commands at staging or production. Provider sandbox validation requires separately approved sandbox credentials and must begin with dry-run/read-only preflight; production writes need separate authorization not contained in this runbook.

Primary signals: pending/claimed/running/retry/dead-letter jobs, oldest queue age, validation and approval latency, operation outcome categories, provider latency/rate limits/permissions, reconciliation queue and incident age, drift, budget exposure, compensation outcomes, worker readiness and schema readiness. `disabled` is an intentional health state; missing schema is unavailable.

## Section 29 test strategy

Automated suites are offline by default and run under the runtime network guard (`tests/helpers/network-guard.js`), which blocks every non-local socket, DNS lookup and fetch; the only permitted destinations are loopback test servers and the local Admin PostgreSQL. Provider behavior is exercised through provider-specific fake transports (`src/modules/marketing/advertising-execution/__tests__/helpers/fake-provider-transports.js`) injected through the production adapter factory and validated against the production host allowlist; a missing fake transport fails closed with `INJECTED_PROVIDER_CLIENT_REQUIRED`. Concurrency-sensitive behavior (SKIP LOCKED claims, queue atomicity, cancellation, creative revisions, evidence immutability) runs against a disposable PostgreSQL database via the `tests/advertising-execution-*postgres*` suites.

Commands: `npm run test:advertising-execution:section29` (aggregate) plus per-suite commands `test:advertising-execution:{plans,policies,approvals,queue-leases,idempotency,providers,creatives,reconciliation,security,docs-migrations,live-harness}`, the durable suites `test:advertising-execution:postgres` and `test:advertising-execution:postgres:sections25-28`, and `test:advertising-execution:all-offline` for the whole domain. All exit non-zero on failure, require no provider credentials and change no tracked files. Requirement-to-test mapping lives in `docs/advertising-execution-section29-test-traceability.md`.

## Section 29.2 live validation

Live provider validation is a separate, explicitly confirmed workflow that never runs from `npm test`, CI, focused suites, pre-commit hooks or migration verification. Every provider remains `NOT_LIVE_VALIDATED` until its live command is deliberately executed and succeeds. Commands: `npm run live:read:<provider>` (read-only capability) and `npm run live:validate:<provider>` (validate-only, and paused writes only with `--confirm-write=YES_CREATE_PAUSED_OBJECTS`). There is intentionally no command that validates all providers at once.

Prerequisites, all mandatory and fail-closed (`scripts/advertising-execution/live-validation-gates.js`): `MARKETING_AD_EXECUTION_LIVE_TEST_CONFIRMED=true` plus the unique confirmation value `MARKETING_AD_EXECUTION_LIVE_TEST_CONFIRMATION=I_UNDERSTAND_THIS_CREATES_PAUSED_PROVIDER_OBJECTS`; a dedicated sandbox/test connection (`--connection-id`, verified sandbox-flagged at runtime); an account allowlist (`MARKETING_AD_EXECUTION_LIVE_TEST_ACCOUNT_ALLOWLIST`) with the production denylist always winning; a Decimal-parsed budget cap (`MARKETING_AD_EXECUTION_LIVE_TEST_MAX_BUDGET_MINOR`, zero-spend preferred) that no API payload can override; a currency allowlist (`MARKETING_AD_EXECUTION_LIVE_TEST_CURRENCY`); a test destination-domain allowlist (`MARKETING_AD_EXECUTION_LIVE_TEST_DESTINATION_ALLOWLIST`); a resource prefix containing `TEST`; an explicit cleanup plan (`--cleanup=pause|archive|delete-if-supported`); operator identity and a reason/change ticket; and a reviewed transport module configured via `MARKETING_AD_EXECUTION_LIVE_TEST_<PROVIDER>_TRANSPORT_MODULE`. Without any one of these the command exits non-zero having made zero provider calls and decrypted zero credentials.

Stage order is fixed: preflight safety → read-only capability → validate-only/dry-run → explicit human write confirmation → paused-resource creation → immediate read-back verification → ledger write → cleanup → cleanup verification → final report. Created resources are forced PAUSED (an active resource aborts the run), use zero-spend or the approved minimal budget, and are recorded in a sanitized ledger under the ignored `artifacts/advertising-execution-live-validation/` directory (run id, provider, API version, safe references, operator, created native ids, parents, statuses, cleanup results, sanitized provider request ids — never tokens, credential envelopes, raw bodies or signed URLs). Cleanup always runs in a finally path and is verified by read-back; incomplete cleanup keeps resources paused, marks manual follow-up, prints the created ids and exits non-zero without erasing the ledger. A provider row may change to `LIVE_VALIDATED` in `docs/advertising-execution-live-validation-matrix.md` only after a successful explicitly confirmed run whose ledger shows verified read-back and verified cleanup.
